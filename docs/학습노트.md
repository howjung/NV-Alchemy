## 1. 전체 구조

```
Flutter 앱 ──▶ Render (Node.js 서버) ──▶ Supabase (PostgreSQL)
 화면, 입력        검사, 로직, 인증            데이터 저장
```

| 이름 | 역할 | 식당 비유 |
| --- | --- | --- |
| Flutter | 앱 화면을 만들고 입력을 받음 | 홀 |
| Node.js | 서버 코드를 실행하는 프로그램 | 주방 |
| NestJS | Node.js 서버 코드를 정리해서 만들게 해 주는 틀 | 주방의 업무 분담표 |
| TypeScript | 타입이 있는 JavaScript. 오타·타입 실수를 미리 알려 줌 | - |
| PostgreSQL | 데이터를 저장하는 DB | 창고 |
| SQL | DB에 저장·조회를 시키는 언어 | 입출고 지시서 |
| TypeORM | TypeScript 코드를 SQL로 바꿔 주는 도구 | 지시서 대필 |
| Supabase | PostgreSQL을 인터넷에서 빌려주는 서비스 | 외부 창고 |
| Render | 서버를 인터넷에서 실행해 주는 서비스 | 가게 자리 |

Docker는 더 이상 쓰지 않는다(예전에는 내 PC에서 DB를 돌릴 때 사용).

**앱은 DB에 직접 접속하지 않는다.** DB 비밀번호가 앱에 들어가면 안 되고, "남의 기록 보기" 같은 것을 서버에서 막아야 하기 때문이다.

## 3. NestJS 핵심 개념

### 3-1. 요청이 지나가는 길
```
GET /          → AppController.getHello() → AppService.getHello() → "Hello World!"
```

| 파일 | 역할 |
| --- | --- |
| `main.ts` | 서버를 켜는 시작점. `listen(포트)` |
| `app.module.ts` | 어떤 부품을 쓸지 묶는 목록 |
| `*.controller.ts` | **어떤 주소**의 요청을 받을지 |
| `*.service.ts` | **실제로 할 일** |
| `*.module.ts` | 기능 하나의 controller와 service를 묶음 |

### 3-2. 용어

| 용어 | 뜻 |
| --- | --- |
| 데코레이터 (`@Get()` 등) | 클래스나 메서드에 "이건 이런 역할이야"라고 붙이는 표시 |
| `@Controller('notices')` | 이 클래스는 `/notices`로 시작하는 주소를 담당 |
| `@Get()` | 조회(GET) 요청을 받는 메서드 |
| `@Injectable()` | 다른 곳에서 가져다 쓸 수 있는 부품 |
| 의존성 주입 | `constructor`에 적으면 NestJS가 객체를 만들어 넣어 줌. 직접 `new` 하지 않음 |
| `imports` | 다른 module을 가져옴 |
| `controllers` | 요청을 받는 클래스 등록 |
| `providers` | 일을 하는 클래스(service) 등록 |
| JSON | 앱과 서버가 데이터를 주고받는 글자 형식 |

### 3-3. HTTP 메서드와 상태 코드

| 메서드 | 용도 | | 코드 | 뜻 |
| --- | --- | --- | --- | --- |
| GET | 조회 | | 200 / 201 | 성공 / 만들기 성공 |
| POST | 만들기 | | 400 | 보낸 값이 잘못됨 |
| PATCH | 일부 수정 | | 401 | 로그인 필요 |
| DELETE | 삭제 | | 404 | 없음 |
| | | | 500 | 서버 오류 |

| 단계 | 내용 | 상태 |
| --- | --- | --- |
| 1 | 프로젝트 생성, 실행 | 코드 정리 완료 (`Hello World!` 화면 확인하면 체크) |

| 4 | Render 배포 | |
| 5 | 가입·로그인 | |
| 6 | 체중·식단 API → 앱 연동 | |

생각해 보기: 왜 데이터를 controller에 바로 적지 않고 service에 둘까?

### 3단계: Supabase 연결

배우는 것: 환경 변수, `.env`, entity, repository

1. 패키지: `npm install @nestjs/config @nestjs/typeorm typeorm pg`
2. Supabase **Connect → Session pooler**의 연결 문자열을 `.env`의 `DATABASE_URL`에 넣는다.
3. `app.module.ts`에 `ConfigModule`, `TypeOrmModule` 설정
4. `Notice` entity(테이블 모양) 만들기
5. service의 배열을 DB 조회로 바꾸기

주의할 것
- `.env`는 `.gitignore`에 있다. **연결 문자열을 코드나 채팅에 쓰지 않는다.**
- 직접 연결 주소가 아니라 **Session pooler**를 쓴다(Render에서 직접 연결 주소는 접속이 안 될 수 있음).
- `synchronize: true`는 entity에 맞춰 테이블을 자동으로 바꾼다. 컬럼이 지워질 수 있으므로 개발 초기에만 쓴다.

확인: Supabase 화면(Table Editor)에 테이블이 생기고, `/notices`가 DB의 데이터를 보여준다.

### 4단계: Render 배포

배우는 것: 배포, 빌드, 환경 변수

1. 서버 코드를 내 GitHub 저장소에 올린다(`.env`가 빠졌는지 확인).
2. Render에서 **Web Service** 생성, 저장소 연결
3. Build Command: `npm install --include=dev && npm run build`
4. Start Command: `npm run start:prod`
5. 환경 변수: `DATABASE_URL`, `NODE_VERSION=22`
6. 확인: `https://<내 서비스>.onrender.com/notices`

무료 요금제: 15분간 요청이 없으면 잠들고, 깨어나는 데 약 1분. 서버에 저장한 파일은 사라질 수 있다. Supabase 무료 프로젝트는 1주일간 안 쓰면 일시 정지된다. **발표 전에 미리 접속해 두기.**

### 5단계: 가입·로그인

배우는 것: 비밀번호 해시, JWT, 입력 검증, 문지기(Guard)

- `POST /auth/signup`, `POST /auth/login`, `GET /users/me`
- 비밀번호는 원문 저장 금지(해시로 저장)
- 로그인하면 토큰(JWT)을 주고, 이후 요청은 `Authorization: Bearer <토큰>`
- `userId`는 body로 받지 않고 토큰에서 꺼낸다(남의 데이터 접근 방지)
- 입력 규칙(PRD): 비밀번호 8자 이상, 닉네임 2~12자, 만 14~100세

### 6단계: 체중·식단과 앱 연동

- CRUD(만들기·조회·수정·삭제), **내 기록만** 접근
- 범위(PRD): 키 100~250cm, 체중 20~300kg, 끼니는 아침·점심·저녁·간식
- 앱 서버 주소를 Render 주소로 바꿔 연결
