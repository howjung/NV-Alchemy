## 1. 제품 개요

### 1.1 한 줄 요약
AI가 분석·추천하는 식단 관리 앱. 식단 기록, 크루 소셜, 쇼핑·정기 배송, 포인트를 한곳에서 제공한다.

### 1.2 문제 정의
- 혼자 하는 다이어트는 동기 부여가 약해 기록과 식단 관리가 오래 이어지지 않는다.
- 기존 앱은 개인 기록·추천 중심이거나, 리워드가 범용 스토어 형태로 연결되어 건강 목적과 맞닿지 않는다.

### 1.3 해결 방안
| 축 | 내용 |
| --- | --- |
| 식단 기록 | 음식 검색·직접 입력으로 칼로리·탄단지를 기록하고 목표 대비 현황을 확인 |
| 크루 소셜 | 크루원과 함께 식단을 인증하고 응원·채팅으로 서로 독려 |
| AI 추천 | 남은 영양소에 맞는 식단 방향과 상품을 제안, 상품별 적합도(%) 제시 |
| 쇼핑·구독 | 밀키트·완제품 구매와 목표 칼로리 기반 정기 배송 |
| 포인트 | 기록 보상으로 적립하고 결제 시 사용 |

### 1.4 타겟 사용자
| 타겟 | 특징 |
| --- | --- |
| 목표형 다이어터 | 기간과 목표를 정해 꾸준히 실천하고 싶은 사용자 (예: 1개월 5kg 감량) |
| 함께할 때 동기가 커지는 사용자 | 지인·같은 목표의 사람과 크루를 이루고 싶은 사용자 |
| 건강식 구매 수요자 | 프로틴·다이어트 밀키트를 간편하게 구매하고 싶은 사용자 |

### 1.5 차별점
| 구분 | 기존 앱 | Antifreeze |
| --- | --- | --- |
| 운영 방식 | 개인 위주 기록, 단순 커뮤니티 | 다이어트 크루 기반 그룹 챌린지 |
| 동기 부여 | 일반 포인트 적립, 기프티콘 교환 | 기록 보상 포인트를 건강 전용 쇼핑 결제에 사용 |
| 게임화 | 단순 출석체크 | 개인 연속 기록(스트릭)과 크루 불꽃 |
| 추천 | 개인 기록 기반 단순 추천 | 남은 영양소 기반 AI 추천과 상품 적합도 |

## 2. 목표와 범위

### 2.1 프로젝트 목표
- 캡스톤 학기 내에 시연 가능한 MVP를 완성한다.
- 기록 → AI 추천 → 구매·구독 → 크루 인증 → 포인트 적립·사용으로 이어지는 핵심 흐름이 끊김 없이 동작한다.

### 2.2 우선순위 기준
| 등급 | 의미 |
| --- | --- |
| P1 | 필수. 없으면 앱이 작동하지 않음 |
| P2 | 핵심. 서비스 주요 기능 |
| P3 | 선택. 완성도 향상 및 보조 |

### 2.3 범위 결정 (v2 확정)
| 항목 | 결정 | 근거 |
| --- | --- | --- |
| 포인트 | 포함 | Figma(CRW-01, MYP-03)와 중간발표 |
| 크루 채팅 | 포함 (Figma CRW-07) | Figma |
| 하단 탭 | 4개 (홈/크루/쇼핑/마이) | Figma. 기록은 홈의 + 버튼으로 처리 |
| 소셜 로그인 | 제외 (이메일 로그인만) | 노션 결정 |
| AI 추천 이력 저장 | 제외 | 노션 결정 |

> v1에서 MVP 제외였던 포인트가 v2에서 포함으로 바뀌었다. 노션 팀 공유 정리(10/9)의 "포인트·벌점·랭킹 제외"는 포인트 부분이 더 이상 유효하지 않다. 벌점·랭킹은 Figma에 화면이 없어 계속 제외한다.

## 3. 사용자 시나리오

1. 가입하고 신체 정보·목표를 입력하면 하루 권장 칼로리가 계산되고, 선호 식단 방식을 고른다.
2. 홈의 + 버튼으로 식단과 체중을 빠르게 기록하고 차트로 현황을 확인한다. 하루 첫 식단 기록에 포인트가 적립된다.
3. 홈의 AI 한마디와 추천 배너가 남은 영양소에 맞는 방향과 상품을 보여주고, 쇼핑에서 적합도(%) 순으로 상품을 본다.
4. 상품 상세에서 단축 구매나 정기구독을 하고, 포인트로 결제 금액 일부를 차감한다.
5. 크루를 만들거나 참가해 식단 인증 글을 올리고 응원·채팅한다.
6. 마이페이지에서 체중 그래프, 구독·배송지·결제 수단, 프로필, 알림을 관리한다.

### 5.3 화면 흐름
- 온보딩: ONB-01 → ONB-02 → ONB-03 → HOM-01
- 홈: HOM-01의 + 버튼 → HOM-02(식단) 또는 HOM-03(체중). HOM-02에서 음식을 추가할 때 HOM-04로 이동
- 크루: CRW-03(진입) → CRW-01(피드) → CRW-07(채팅), CRW-08(관리). 검색은 CRW-02 → CRW-05. 생성은 CRW-04 → CRW-06
- 쇼핑: SHO-01 → SHO-03 → SHO-02(단축 구매) 또는 SHO-04(구독 설정)
- 마이: MYP-01(허브) → MYP-02, 03, 04, 05. MYP-02에서 SHO-05, SHO-06 호출

### 5.4 화면 유형 기준
- 전체화면: 탭 이동, 정보량이 많은 화면
- 바텀시트: 현재 화면을 유지한 채 빠르게 입력·결제
- 모달: 확인·취소·신청 같은 의사결정

## 6. AI 활용

| 위치 | 기능 |
| --- | --- |
| 온보딩 | 신체 정보로 권장 칼로리 계산 |
| 홈 | AI 한마디: 남은 영양소 기반 안내. 누르면 도움말 시트 |
| 홈 | AI 추천 시트: 저녁 식단 방향 제안과 계산 근거("이렇게 계산했어요") 공개 |
| 쇼핑 | 상품별 적합도(%)와 AI 추천순 정렬, 남은 영양 요약 |
| 마이 | 선호 식단 방식 설정이 홈·쇼핑 추천에 반영 |

- AI 호출은 서버에서만 한다. 호출 실패 시 AI 요소를 숨기거나 기본값을 보여준다.
- AI 호출 중에는 로딩 상태를 보여준다.
- 추천 결과는 DB에 저장하지 않는다.

## 8. 기술 스택과 데이터

### 8.1 기술 스택
| 구분 | 기술 | 근거 |
| --- | --- | --- |
| 앱(Frontend) | Flutter (VS Code) | 확정 |
| 서버(Backend) | Node.js (Express) REST API | 팀 결정 |
| DB | PostgreSQL | 팀 결정 (중간발표의 MariaDB에서 변경) |
| AI | Gemini API (Flash 계열) | 확정 |
| 협업 | Figma, GitHub, Notion | 중간발표 |

> Python은 사용하지 않는다. 중간발표의 Python 3.14와 MariaDB는 폐기하고, 서버와 AI 호출 모두 Node.js로 구현한다.
> 노션의 React + Supabase 구성도 폐기한다. 별도 서버가 생기므로 인증, 주문, 구독, AI 호출, 탈퇴는 모두 Node.js API로 구현한다.

### 8.2 데이터 모델
노션 ERD 초안(14개 테이블)을 기준으로 하고 v2에서 필요해진 테이블을 추가한다.

- 기존 14개: `users`, `goals`, `weight_logs`, `meal_logs`, `meal_items`, `crews`, `crew_members`, `crew_posts`, `crew_comments`, `product_categories`, `products`, `orders`, `order_items`, `subscriptions`
- 추가 제안: `point_ledger`(적립·사용 내역), `crew_messages`(채팅), `addresses`, `payment_methods`, `foods`(음식 DB)
- `crew_members`가 사용자와 크루의 다대다를 푼다. 상태 컬럼으로 신청 대기·가입을 구분한다.
