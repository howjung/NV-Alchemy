## 1. 제품 개요

### 1.1 한 줄 요약
AI가 분석·추천하는 식단 관리 앱. 식단 기록, 크루 소셜, 쇼핑·정기 배송, 포인트를 한곳에서 제공한다.

### 1.2 문제 정의
- 혼자 하는 다이어트는 동기 부여가 약해 기록과 식단 관리가 오래 이어지지 않는다.
- 기존 앱은 개인 기록·추천 중심이거나, 리워드가 범용 스토어 형태로 연결되어 건강 목적과 맞닿지 않는다.

### 1.3 해결 방안
| 축 | 내용 |
| --- | --- |
| 식단 기록 | 끼니별로 칼로리·탄단지를 기록하고 목표 대비 현황을 확인 |
| 크루 소셜 | 크루원과 함께 식단을 인증하고 불꽃 보내기·댓글로 서로 독려 |
| AI 추천 | 남은 영양소에 맞는 식단 방향과 상품을 제안, 상품별 적합도(%) 제시 |
| 쇼핑·구독 | 샐러드·밀키트·도시락·단백질 상품의 가격 비교, 장바구니 주문, 정기 배송 |
| 포인트 | 기록 보상으로 적립하고 결제 시 사용 |

### 1.4 타겟 사용자
| 타겟 | 특징 |
| --- | --- |
| 목표형 다이어터 | 기간과 목표를 정해 꾸준히 실천하고 싶은 사용자 (예: 1개월 5kg 감량) |
| 함께할 때 동기가 커지는 사용자 | 지인·같은 목표의 사람과 크루를 이루고 싶은 사용자 |
| 건강식 구매 수요자 | 프로틴·다이어트 밀키트를 간편하게 구매하고 싶은 사용자 |

### 1.5 차별점
| 구분 | 기존 앱 | Antifreeze |
| --- | --- | --- |
| 운영 방식 | 개인 위주 기록, 단순 커뮤니티 | 다이어트 크루 기반 그룹 챌린지 |
| 동기 부여 | 일반 포인트 적립, 기프티콘 교환 | 기록 보상 포인트를 건강 전용 쇼핑 결제에 사용 |
| 게임화 | 단순 출석체크 | 개인 연속 기록(물방울·캐릭터 보상)과 크루 연속 인증 |
| 추천 | 개인 기록 기반 단순 추천 | 남은 영양소 기반 AI 추천과 상품 적합도 |

## 2. 목표와 범위

### 2.1 프로젝트 목표
- 캡스톤 학기 내에 시연 가능한 MVP를 완성한다.
- 기록 → AI 추천 → 구매·구독 → 크루 인증 → 포인트 적립·사용으로 이어지는 핵심 흐름이 끊김 없이 동작한다.

### 2.2 우선순위 기준
| 등급 | 의미 |
| --- | --- |
| P1 | 필수. 없으면 앱이 작동하지 않음 |
| P2 | 핵심. 서비스 주요 기능 |
| P3 | 선택. 완성도 향상 및 보조 |

최종 Figma에는 우선순위가 없다. 4장의 우선순위는 v6 표의 값 중 기능이 같은 것을 유지했고, 새로 생긴 기능은 "P? (제안값)"으로 제안했다.

## 3. 사용자 시나리오

1. 앱을 열면 SPLASH 후 로그인한다. 처음이면 약관에 동의해 가입하고, 프로필 정보(닉네임·생년월일·성별)와 신체 정보·목표를 입력해 하루 권장 칼로리를 계산한다.
2. 홈 탭에서 끼니별 + 버튼으로 식단을, "체중 기록하기"로 체중을 기록한다. 하루 첫 식단 기록에 5P가 적립되고 연속 기록이 늘어난다.
3. 기록 탭에서 날짜별 칼로리·탄단지, 끼니별 기록, 체중·BMI를 확인하고 AI 추천 시트로 저녁 식단 방향을 본다.
4. 쇼핑 탭에서 남은 영양소 기준 AI 적합도(%)로 상품을 보고, 판매처별 가격을 비교해 장바구니에 담는다. 주문·결제에서 포인트를 쓰거나 정기 배송을 신청한다.
5. 소셜 탭에서 크루를 만들거나 참가해 식단 인증 게시물을 올리고, 불꽃 보내기·댓글로 서로 응원한다. 전체 피드에서 공개 게시물도 본다.
6. 프로필 탭에서 체중 변화 그래프, 주문·구독 내역, 배송지·결제 수단, AI 추천·알림 설정, 계정, 고객 지원을 관리한다.

## 4. 기능 요구사항

도메인은 `auth`, `profile`, `record`, `point`, `social`, `shop`, `notification`, `support` 8개다. 번호 `#`는 노션 기능 목록표 순번이고, `N`은 중간발표 또는 최종 Figma에서 새로 확인된 기능이다. 화면 ID는 최종 Figma 프레임 이름의 ID를 쓰고, ID가 없는 화면은 프레임 이름 그대로 쓴다.

- 한 기능이 여러 행으로 나뉜 경우 같은 `#` 번호를 쓴다.
- "구현 방식"은 화면이 없는 서버 전용 기능에만 쓰며 4.9에 모았다.
- 수치·규칙에 붙은 "(제안값)"은 계획 단계의 제안이며, "(확정 필요)"는 팀 확정 전까지 값을 정하지 않은 것이다. 확정 필요 항목은 9장에 모았다.
- 텍스트가 없는 화면(프로필 04~20 중 일부)은 화면 이름과 존재만 적고 상세 규칙은 (확정 필요)로 둔다.

### 4.10 수락 기준

| 연속 기록 | 어제 기록이 없는 상태로 홈에 진입한다 | 연속 0일을 표시하고 H7 안내 팝업을 1회 보여준다 |
| 포인트 사용 | 사용 포인트가 1~499P, 100 단위가 아닌 값, 결제 금액 초과 (0P는 포인트 미사용으로 정상 처리) | 요청을 거부하고 사유를 표시한다 |
| 포인트 환급 | 취소 가능한 주문을 취소한다 | 사용 포인트가 point_ledger에 전액 환급 적립된다 |
| 가격 비교 | 상품 카드의 "가격 비교 N곳"을 펼친다 | 판매처별 가격·배송비·합계를 보이고, 카드의 최저가는 합계 최소값과 같다 |
| 장바구니 | 상품을 담고 빼고 S3로 이동한다 | 하단 바의 개수·합계가 장바구니와 일치하고, 결제 예정 금액이 상품 금액과 배송비 합과 같다 |
| 구독 | 해지 기한(다음 배송일 전날 23:59:59 KST)이 지난 뒤 해지를 요청한다 | 요청을 거부하고 사유를 표시한다 |

| AI | AI 호출이 실패한다 | AI 영역을 숨기고 나머지는 정상 동작한다. 홈에 다시 들어와도 AI를 호출하지 않는다 |

### 8.1 기술 스택

> Python은 사용하지 않는다. 중간발표의 Python 3.14와 MariaDB는 폐기하고, 서버와 AI 호출 모두 Node.js로 구현한다.
> 노션의 React + Supabase 구성도 폐기한다. 별도 서버가 생기므로 인증, 주문, 구독, AI 호출, 탈퇴는 모두 Node.js API로 구현한다.

### 8.2 데이터 모델
노션 ERD 초안(14개 테이블)을 기준으로 하고 v2~v7에서 필요해진 테이블을 추가한다.

- 기존 14개: `users`, `goals`, `weight_logs`, `meal_logs`, `meal_items`, `crews`, `crew_members`, `crew_posts`, `crew_comments`, `product_categories`, `products`, `orders`, `order_items`, `subscriptions`
- 유지한 추가 제안(v2~v6): `point_ledger`(적립·사용 내역), `addresses`(사용자당 다건), `payment_methods`(사용자당 다건), `foods`(음식 DB), `crew_post_likes`(게시글·사용자 복합 유일키)
- v7 추가 제안:
  - `sellers`(판매처)와 `offers`(상품·판매처별 가격, 배송비. 최저가 = 가격 + 배송비의 최소). 가격은 예시 데이터이며 수집 방식은 (확정 필요, N2)
  - `cart_items`(사용자, 상품, 판매처 offer, 수량)
  - `notifications`(사용자, 종류, 내용, 읽음 여부, 생성 시각)
  - `user_blocks`(차단자·피차단자 복합 유일키), `post_reports`(게시물, 신고자, 사유, 처리 상태), `post_hides`("관심 없음" 처리)
  - `notices`(공지), `faqs`(자주 묻는 질문), `inquiries`(1:1 문의). 관리 방식은 (확정 필요, N18, N19)
  - `user_rewards`(연속 기록 마일스톤 달성과 꾸미기 보상). 꾸미기 항목 정의는 (확정 필요, N11)
  - `crew_post_flames`("불꽃 보내기" 기록). 좋아요와 통합할지는 (확정 필요, N13)
- 변경: `crew_messages`(채팅)는 삭제했다. `crew_posts`에는 공개 범위(공개/비공개/크루만 공개)와 미디어 종류(사진/비디오)를 둔다. 크루 없이 올리는 게시물의 처리와 SOC-08 전체 피드 노출은 (확정 필요, N16)
- `users` 컬럼에 선호 식단 방식과 알림 설정을 둔다. 알림 설정 항목은 (확정 필요, N1). `subscriptions`에는 패키지 또는 상품, 배송 주기, 배송 요일, 수량, 다음 배송일, 건너뛰기 횟수, 다음 주 메뉴를 둔다(N4, N8).
- `crew_members`가 사용자와 크루의 다대다를 푼다. 상태 컬럼으로 신청 대기·가입을 구분한다.
- `point_ledger` 사유는 식단 기록, 쇼핑 결제 사용, 주문 취소 환급, 크루 리워드(확정 필요, N10)로 구분한다.

### 9.4 프롬프트에서 사용 중인 임시값
단계별 프롬프트 파일이 쓰는 임시값이다. 프롬프트 파일은 이 문서(v8) 기준으로 맞췄다. 확정 전까지 이 값으로 구현한다.

| 항목 | 임시값 |
| --- | --- |
| 권장 칼로리 하한 | 남성 1500kcal, 여성 1200kcal |
| 음식 DB | 자체 시드 30개 |
| 판매처 가격 | 예시 데이터 시드 (N2 확정 전) |
| 결제 | 모의 결제 |
| 과식 기준 | 전날 권장 칼로리보다 500kcal 이상 |
| 크루 가입 | 1인 1크루 |
| 크루장 탈퇴 | 탈퇴 없이 크루 삭제만 가능(Figma 크루장 메뉴 기준). 위임 방식은 쓰지 않음 |

## 10. 바이브코딩 단계 (제안)

화면 71개(5.2)를 5단계에 나눈다. 화면 수는 단계 열의 합이다.

| 단계 | 내용 | 화면 | 기능 |
| --- | --- | --- | --- |
| 1 | 서버·앱 세팅(하단 탭 5개 뼈대), DB, 인증, 온보딩, 약관 정적 화면 | SPLASH, AUTH-02~04(+전송 완료), ONB-01(+생년월일 시트), ONB-02, 프로필 07·17·20 (11개) | #1, #2, 세션 유지, 비밀번호 찾기, 약관 |
| 2 | 홈·기록, 식단·체중 기록, 포인트 적립·연속 기록, 알림 목록, 체중 그래프, 프로필 메인·신체 지표 | HOM-01, NOT-03, MYP-03, SHT-P01, HOM-03, MYP-04E, H7, 식단 기록 시트, 홈 AI 한마디 도움말, 기록, 기록 캘린더, 기록 AI 추천 시트, 프로필 메인, 프로필 04·04E (15개) | #4, #5, #18, #19, 포인트 적립·내역, 연속 기록 |
| 3 | 쇼핑 메인(판매처 가격 비교), 장바구니, 주문·결제, 포인트 사용, 주문 취소 환급(API) | S1, S3, S4, S5, S6, 상품 상세 시트, 장바구니 빼기 확인 (7개) | #13, #14, 가격 비교, 장바구니, 포인트 사용 |
| 4 | 주문·구독 내역과 상세, 정기 배송·구독 관리, 배송지·결제 수단, AI 연동(Gemini), 알림·AI 추천 설정 | S7, S8, S9, S10, S11, 주문 취소 확인, 프로필 05·06·13·13E·14, 배송지 삭제 팝업 (12개) | #7, #15, #16, #17, #20, 주문 취소, 배송지·결제 수단, 알림 설정, AI 추천 설정 |

> 1~2단계의 AI 영역(홈 AI 한마디, 기록 AI 추천 시트, S1 적합도)은 화면만 만들고, 4단계에서 Gemini 호출을 연결한다. 그 전에는 AI 영역을 숨기거나 기본 문구를 쓴다(6.1).
